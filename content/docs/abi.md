Slung loads `wasm32-wasip1` modules. The host discovers source, component, mapper, and rule descriptors from Wasm exports, then provides runtime functions through the `env` import module.

The Rust SDK is the supported way to produce modules. This page describes the contract for SDK authors and people implementing another language SDK.

## Guest exports

A module may export descriptors and entrypoints generated by the SDK. The host uses those exports to build the capability graph. Mappers receive raw source bytes and write mapped component bytes into guest memory. Rules are invoked with the current entity and rule context supplied by the host runtime.

Modules that return host-allocated buffers must export:

```text
slung_alloc(len: usize) -> *mut u8
slung_dealloc(ptr: *mut u8, len: usize)
```

The host calls `slung_alloc` before copying response or component data into guest memory. The guest owns the returned allocation and must release it with `slung_dealloc` when the SDK wrapper is finished.

## Generic host functions

All generic functions are imported from `env`:

```text
slung_get(entity_id, component_id, out_ptr, out_len) -> status
slung_set(entity_id, component_id, value_ptr, value_len) -> status
slung_now(wall_hi_ptr, wall_lo_ptr, logical_ptr) -> status
slung_yield() -> status
```

`slung_get` returns JSON bytes allocated in guest memory. A missing value returns a non-zero status with a zero pointer and length.

`slung_set` consumes JSON bytes from guest memory, updates active state, and schedules dependent rules. A successful return means the write was accepted and signalled; it does not mean every downstream rule has completed.

`slung_now` writes the HLC wall-clock high word, wall-clock low word, and logical counter to guest memory.

The Rust SDK normally hides these raw calls behind `RuleContext::get`, `RuleContext::set`, `RuleContext::now`, and `RuleContext::yield_now`.

## Outbound HTTP

Outbound HTTP functions are imported from `env`:

```text
slung_http_get(url_ptr, url_len,
              request_headers_ptr, request_headers_len,
              response_ptr, response_len,
              response_headers_ptr, response_headers_len) -> status

slung_http_delete(...) -> status

slung_http_post(url_ptr, url_len,
                request_headers_ptr, request_headers_len,
                body_ptr, body_len,
                response_ptr, response_len,
                response_headers_ptr, response_headers_len) -> status

slung_http_put(...) -> status
```

Request headers and response headers use a repeated binary entry format:

```text
u32 name_length   little-endian
u32 value_length  little-endian
[name bytes]
[value bytes]
```

The request header buffer is supplied by the guest. Response body and response-header buffers are allocated with `slung_alloc` and must be released with `slung_dealloc`.

HTTP status codes are returned directly. For example, `200`, `404`, and `500` are all valid response statuses. A return value of `0` means that no HTTP response was received because the transport request failed before a response was available.

The Rust SDK exposes this as:

```rust
use slung::host::http;

let response = http::post(
    "http://service.internal/orders",
    br#"{"id":"order-123"}"#,
    &[
        ("Content-Type", "application/json"),
        ("Idempotency-Key", "order-123"),
    ],
)?;

if response.status == 201 {
    // response.headers: Vec<(String, String)>
    // response.body: Vec<u8>
}
```

The runtime does not retry outbound requests automatically and does not provide exactly-once external effects. Use an application idempotency key at the destination when a rule may be replayed after recovery.

## ABI and durability

The ABI status of `slung_set` describes acceptance into the runtime, not durable completion of the full cascade. Source transport responses likewise are not automatically durability acknowledgments.

Durability is selected by host configuration, not by the Wasm module:

+ `eventual`: enqueue checkpoints and continue;
+ `strict`: wait for the WAL write and sync.

See [Deployment and configuration](/docs/deployment) for configuration and [Rules](/docs/rules) for propagation semantics.
